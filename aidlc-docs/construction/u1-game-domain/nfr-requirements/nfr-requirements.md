# U1 NFR 需求

## 性能

1. 在普通开发笔记本的 Node.js 环境中，`createLevel`、`reduce` 和 `toViewModel` 的单次调用目标均低于 5 ms。
2. 性能检查以 1,000 次受控迭代的抽样统计执行，排除首次模块加载和测试框架启动开销；它是防回归目标，不是浏览器帧/服务 SLA。
3. U1 不执行 I/O、网络、DOM、WebGL、音频或持久化；每次调用的工作量受关卡参数上限和第 8 关难度上限约束。

## 可靠性与确定性

1. 相同 `(levelNumber, baseSeed)` 与相同行动/时间序列必须产生结构相同的关卡和可观察等价的状态/效果序列。
2. 所有 reducer 操作必须为总函数：未知、非法或时机不当的动作返回安全不变状态或白名单拒绝效果，不抛出未处理异常。
3. 生命保持在 0–3，分数和最高分非负，时间单调，阶段与活动跳跃关系一致。
4. 测试运行时必须报告失败种子和收缩后的反例，以便复现和修复。

## 安全与数据保护

1. U1 不接收网络请求、用户文本、认证数据、密钥、令牌或个人数据；不写入日志、文件或浏览器存储。
2. 所有外部影响经受限 `GameAction`/`GameEffect` 枚举边界传递；禁止任意字符串、异常对象和浏览器全局对象进入领域状态或效果。
3. 供应链依赖必须使用精确版本并由 lockfile 固定；仅从官方 npm 注册表获取开发依赖。
4. 项目需在质量流程中执行 `npm audit`，并提供 SBOM 生成说明；高严重度发现不得被静默忽略。

## 可测试性

1. 使用 `node:test` 执行示例测试，使用 `fast-check` 执行属性测试；两类测试文件按命名分开。
2. 每一关键玩家路径至少有一个示例测试；关卡可达性、确定性、木板边界、状态机、得分/生命范围和视图模型纯度必须有 PBT。
3. 属性生成器必须是领域约束的可复用工具，覆盖边界输入；不得用无约束原始对象替代。
4. PBT 框架必须保持收缩能力，测试命令必须保留失败种子；禁止通过重试掩盖不稳定失败。

## 可维护性

1. U1 维持纯函数边界，公开 API 在单个 `game.js` U1 章节中集中导出；不得与 U2 共享隐藏可变状态。
2. 每项业务规则应可追溯至需求/故事/功能设计和一个示例或属性测试。
3. 测试与格式检查必须在本地可重复运行；新增依赖须证明实际使用并记录用途。

## 可用性、扩缩与可用性说明

- 用户界面无直接归属 U1；无障碍和视觉反馈属于 U2。
- U1 没有服务端负载、跨实例扩缩、灾备、可用性 SLA、远程监控或告警要求。
- U1 失败通过返回受控领域结果而非服务降级；其正确性由本地自动化测试与最终浏览器集成冒烟验证保证。

## 扩展合规

### Security Baseline

- **适用且合规设计**：SECURITY-09（支持版本、无默认凭证）、SECURITY-10（精确依赖/锁文件/审计/SBOM）、SECURITY-11（白名单动作与业务滥用防护）、SECURITY-13（官方注册表和依赖完整性流程）、SECURITY-15（总函数与安全失败）。
- **N/A**：SECURITY-01 至 08、12、14；U1 无持久化、网络中间层、应用服务、API、IAM、网络、认证或远程日志/告警。

### Property-Based Testing

- **PBT-09 合规**：`fast-check` 被选为唯一属性测试框架；其必须以精确版本放入开发依赖并与 `node:test` 集成。
- **后续强制项**：实现 PBT-03、05、06、07、08、10；PBT-02/04 在未添加相关功能前保持 N/A。
